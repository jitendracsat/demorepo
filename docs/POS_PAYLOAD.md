# POS Payload Specification

## Overview

When a guest confirms an order, the Node.js backend constructs a POS-formatted JSON payload and logs it. This document defines the exact structure, field names, types, and sourcing for every field in that payload.

The payload is assembled in `backend/controllers/orderController.js` and is returned in the API response as `posPayload` alongside the persisted order record.

## Field Reference

### Root Level

| Field | Type | Source | Notes |
|---|---|---|---|
| `outletId` | `string` | Request body → `outletId` | Outlet identifier in the POS system |
| `restaurantid` | `string` | Request body → `restaurantId` | Restaurant identifier; **lowercase `id`** to match POS contract |
| `OrderId` | `string` | Generated by backend | Sequential format: `ORD000001`. Padded to 6 digits. Stored in `Order.orderId` |
| `OrderDate` | `string` (ISO 8601) | `new Date().toISOString()` at creation time | UTC timestamp |
| `PosCode` | `string` | Request body → `posCode` | Terminal/station code used by the POS |
| `TblNo` | `string` | Request body → `tableNumber` | Restaurant table identifier (e.g., `A-12`, `5`) |
| `subtotal` | `number` (float) | Request body → `billDetails.subtotal` | Pre-tax, pre-discount item total |
| `discountAmount` | `number` (float) | Request body → `billDetails.discountAmount` | Total discount applied across the order |
| `taxAmount` | `number` (float) | Request body → `billDetails.taxAmount` | Tax component (GST / service charge) |
| `totalAmount` | `number` (float) | Request body → `billDetails.total` | Final payable amount: `subtotal - discount + tax` |
| `paymentMethod` | `string` | Request body → `paymentMethod` | Accepted values: `CASH`, `UPI`, `CARD` |
| `currency` | `string` | Hardcoded | Always `"INR"` |
| `guest` | `object` | See Guest Object below | Guest CRM information |
| `items` | `array` | See Item Object below | Ordered line items |

---

### Guest Object

| Field | Type | Source | Notes |
|---|---|---|---|
| `guestId` | `string` | Request body → `guestId` | Typically the guest's phone number, used as CRM key |
| `name` | `string` | Request body → `guestName` | Guest display name |
| `phone` | `string` | Request body → `guestPhone` | Mobile number (without country code) |
| `email` | `string` | Request body → `guestEmail` | Guest email address |
| `dateOfBirth` | `string` | Request body → `guestDob` | Format: `DD/MM/YYYY`. Empty string if not provided |
| `anniversary` | `string` | Request body → `guestAnniversary` | Format: `DD/MM/YYYY`. Empty string if not provided |

---

### Item Object

Each element in the `items` array represents a single menu line item.

| Field | Type | Source | Notes |
|---|---|---|---|
| `itemId` | `string` | Cart item → `itemId` | POS menu item identifier |
| `itemName` | `string` | Cart item → `itemName` | Display name of the item |
| `category` | `string` | Cart item → `category` | Menu category (e.g., `MAIN COURSE`, `BREAD`, `BEVERAGES`) |
| `quantity` | `number` | Cart item → `quantity` | Ordered quantity (integer in practice, stored as float) |
| `unitPrice` | `number` (float) | Cart item → `unitPrice` | Price per single unit |
| `totalPrice` | `number` (float) | Cart item → `totalPrice` | `quantity × unitPrice` |
| `modifiers` | `array` | Cart item → `modifiers` | Array of modifier objects (e.g., spice level, add-ons). Empty array if none |
| `discountApplied` | `number` (float) | Cart item → `discountApplied` | Item-level discount. `0.00` if none |

## Field Name Casing Note

The POS system contract uses **mixed casing** for top-level keys. This is intentional and must not be normalised:

| Field | Casing | Reason |
|---|---|---|
| `outletId` | camelCase | POS contract |
| `restaurantid` | all-lowercase | POS contract — note the lowercase `id` |
| `OrderId` | PascalCase | POS contract |
| `OrderDate` | PascalCase | POS contract |
| `PosCode` | PascalCase | POS contract |
| `TblNo` | PascalCase | POS contract |
| `guest`, `items` | lowercase | POS contract |

Do not rename or normalise these fields without confirming the change with the POS integration team.

## Order ID Generation

External order IDs are generated sequentially by the backend at order creation time:

```
ORD + zero-padded count of existing orders + 1
```

Example: if 42 orders exist in the database, the next `OrderId` will be `ORD000043`.

This ID is stored in `Order.orderId` and is distinct from the internal `Order.id` (UUID), which is used for all internal and API lookups (e.g., `/api/orders/:id`, `/bill/:id`).
